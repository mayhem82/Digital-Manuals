# Digital Manuals — Can-Am Spyder RT/RT-S (2010-2011)

A structured digital workshop manual, built to the spec in [`BUILD.md`](./BUILD.md):
extracted text, structured procedures/specs/fault codes/glossary, retained
diagrams, deterministic search, and offline use — **not** a wrapped PDF and
not an AI diagnostic assistant.

## Current build status

**Architecture is built. Ingestion is underway; text extraction is blocked on a font issue for 9 of the 10 registered documents.**

The source PDF (`source-pdf/spyder-rt-rts-2010-2011-service-parts.pdf`, 1,603
pages) has been ingested for text on every compilation page. Only the main
shop manual (`DOC-SPYDER-SHOP`, 685 of 779 pages) came out as real, readable
text — see `data/documents.json`. Every other document (RT-622 trailer
manual, flat-rate manual, all six parts-catalogue year/model splits, and the
2011 Technical Update Book) uses a font the source PDF embeds without a
usable ToUnicode CMap, so pdfplumber/PyMuPDF cannot recover real characters
from any page in those ranges — each document's `status` field reads
`TEXT_LAYER_UNUSABLE_BROKEN_FONT`, and every one of those pages is recorded
in `scripts/ingest/human-review-queue.json` rather than displayed as if it
were readable (BUILD.md section 7). Getting real text out of those 9
documents will need OCR or another extraction approach — not yet done.

For `DOC-SPYDER-SHOP`, a 2-level table of contents (`data/toc.json`) is built
from the manual's own running page headers, and `data/glossary.json` has 27
terms seeded from the manual's own acronym table and sensor headings.
`DOC-RT622-SHOP`'s TOC uses the PDF's own outline directly (reliable) but has
no resolved page destinations, since none of its pages are machine-readable
yet. `data/procedures.json`, `data/specifications.json`,
`data/fault-codes.json`, `data/diagrams.json`, `data/parts-links.json`,
`data/technical-updates.json`, and `data/cross-references.json` are still
empty. `data/manifest.json` is generated by
`scripts/build/generate-manifest.mjs` from actual file contents, so it
honestly reports current counts, not targets — see BUILD.md section 24:
nothing here is described as complete before it's verified.

The known documented source gaps (BUILD.md section 4) are already recorded
in `data/source-gaps.json` and rendered in the app's **Source Gaps** view.
Note: the broken-font issue above is a *readability* problem, not a *source
gap* — those pages are physically present in the compilation, just not yet
machine-readable.

## What's implemented

- Full repository architecture per BUILD.md section 6.
- Data schemas for documents, pages, TOC, procedures, specifications, fault
  codes, glossary, diagrams, parts links, technical-update relationships,
  cross-references, source gaps, and search aliases.
- A deterministic, layered search engine (`src/search`) — exact text, TOC
  headings, glossary/component/owner-language aliases, fault-code lookup,
  part-number lookup. No LLM reinterprets queries at runtime.
- Glossary module that makes known terms tappable inside rendered page text.
- Bookmarks/notes with JSON export/import (not just `localStorage`).
- Applicability filters (2010/2011/RT/RT-S/SM5/SE5/RT-622) that show
  "unknown" rather than hiding content of unknown applicability.
- A mobile-first, dark-mode-aware UI with a desktop split-view breakpoint,
  large tap targets, and sticky search — see BUILD.md sections 21-22.
- `scripts/validate/validate.mjs` — fails the build on broken TOC
  destinations, broken asset references, unresolved cross-references,
  duplicate IDs, missing source references, or a `VERIFIED` item without
  verification metadata (BUILD.md section 26).
- `scripts/build/generate-manifest.mjs` — regenerates `data/manifest.json`
  from actual counts on every build; never hand-edited.
- `scripts/ingest/extract_text.py` and `extract_visuals.py` — functional
  ingestion scripts, ready to run once the source PDF compilation is
  available locally. See `scripts/ingest/README.md`.
- GitHub Pages deploy workflow (`.github/workflows/deploy.yml`) that runs
  validation and manifest generation before every deploy.
- PWA manifest + service worker for offline use after first load.

## Running ingestion

Once the source PDF is available on a machine you control:

```
pip install pdfplumber pymupdf
python3 scripts/ingest/extract_text.py --pdf /path/to/compilation.pdf --document DOC-SPYDER-SHOP --compilation-range 1 400
python3 scripts/ingest/extract_visuals.py --pdf /path/to/compilation.pdf --document DOC-SPYDER-SHOP --manifest visuals-manifest.json
npm run validate
npm run manifest
```

See `scripts/ingest/README.md` for the full pipeline, including why
source/manual page numbers are never derived from a guessed global offset
(BUILD.md section 5).
